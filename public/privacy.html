Board Room — Privacy Policy

Effective 1 August 2026 · Reviewed annually

Board Room is a private application with a single user: its owner. It is not a product, it has no customers, no employees and no contractors. It exists so one person can read their own household data — a grocery list, a calendar, their own bank transactions — in one place. Nothing here is sold, shared for advertising, or used to train anything.

What is collected

  • Financial data, via Plaid. When the owner connects a bank account through Plaid Link, this application receives transactions (date, amount, description, merchant, the bank's own category) and account details (account name, type, the last four digits, and balances).
  • Account data. An email address and password hash, held by Supabase, used only to sign in.
  • Everything else the owner types into it — lists, notes, budgets, dates.

Bank credentials are never seen or handled by this application. They are entered into Plaid Link, which communicates with the financial institution directly. This application receives only a Plaid access token, and never a username, password or one-time code.

How it is used

Only to display it back to the owner: to total a month, categorise spending against budgets, and show current balances. There is no other use. It is not shared with any third party, not sold, not used for advertising or profiling, and no automated decision is made from it.

Consent

Data is collected only when the owner explicitly connects an account through Plaid Link, which presents Plaid's own consent screen and end-user privacy policy before anything is shared. Connecting is an affirmative action taken by the person whose data it is. It can be withdrawn at any time — see Deletion, below.

Storage and security

  • In transit: HTTPS with TLS 1.2 or better, everywhere, enforced by the hosting providers. There is no unencrypted endpoint.
  • At rest: data is stored in a managed PostgreSQL database (Supabase), encrypted at rest with AES-256.
  • Row-level security is enabled on every table, scoped so that a signed-in session can read only rows belonging to that user.
  • Plaid access tokens are held in a table with row-level security enabled and no policy at all, with all privileges revoked from the browser-facing database roles. They are readable only by the server-side function that uses them, and are never sent to the browser.
  • API secrets (including the Plaid secret) exist only as environment variables on the server-side functions. They are not in the source repository, not in the client bundle, and builds fail automatically if a secret would be published.
  • Balances are never stored. They are fetched when the page is opened and discarded when it is closed.
  • Access to the systems that hold this data (Supabase, Netlify, GitHub, the Plaid dashboard) is limited to the single owner, protected by multi-factor authentication.

Service providers

Three, each acting as a processor for this application:

  • Plaid Inc. — the connection to financial institutions. Plaid's end user privacy policy.
  • Supabase — the database and authentication (SOC 2 Type II).
  • Netlify — hosting and server-side functions (SOC 2 Type II).

There are no others. No analytics service, no advertising network, no data broker, and no tracking cookies of any kind — the only browser storage used is the session that keeps the owner signed in.

Retention and deletion

Financial data is retained only while it is useful to the person it belongs to, and is deleted on request without delay. In practice:

  • Disconnecting a bank in the app calls Plaid's /item/remove, which ends Plaid's access to the institution, and deletes the stored access token immediately.
  • Removing an account's transactions deletes those rows from the database.
  • Deleting the user account removes every row associated with it; database foreign keys are declared on delete cascade, so nothing is left behind.
  • Balances are never written to storage at all, so there is nothing to delete.
  • Data is not retained after deletion for any secondary purpose. Provider backups age out on the hosting providers' own schedules.

This policy is reviewed at least once a year, and whenever the application's handling of data changes.

Rights

The only person whose data this application holds is its owner, who can export, correct or delete any of it at any time from within the application.
